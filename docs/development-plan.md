## 1. 技術選定

要件4.2の推奨をほぼそのまま採用する。変更・具体化した点のみ根拠を記す。

| 領域 | 採用 | 補足・根拠 |
| --- | --- | --- |
| パッケージ管理 | **pnpm workspaces** | モノレポの依存解決が高速・厳密。Docker ビルドでも扱いやすい |
| 言語 | TypeScript（strict） | 共有パッケージで型・バリデーション・計算ロジックをフロント/サーバー共通化 |
| フロントエンド | React 18 + Vite + React Router | 1アプリを `/register` `/kitchen` `/customer` `/pickup` `/admin` に分割 |
| UI 状態 | TanStack Query（取得系）＋ Zustand（端末ローカル状態） | 再接続時の全状態再取得を Query の invalidate で素直に書ける |
| スタイル | CSS Modules（＋CSS変数） | 外部CDN・Webフォント禁止（要件4.1）。システムフォントのみ使用 |
| サーバー | **Fastify** | Socket.IO との統合実績が多く、スキーマ検証・プラグイン構成が成熟。Hono より Node 専用運用での情報量が多い |
| リアルタイム | **Socket.IO** | 自動再接続・ルーム（役割/ステーション別配信）・ACK を標準で持つ |
| バリデーション | **Zod**（shared に定義） | API入力・WSイベントの型と実行時検証を1か所で定義 |
| DB | SQLite（WAL）+ **better-sqlite3** + **Drizzle ORM** | better-sqlite3 は同期APIで `BEGIN IMMEDIATE` トランザクションを確実に張れる → 採番の排他が単純かつ確実。Drizzle は PostgreSQL 方言にも対応 |
| 認証 | PIN/パスワード: **argon2**、セッション: 署名付き Cookie | 端末トークン（ペアリング）と従業員セッションを分離 |
| PDF | **pdfkit**（サーバー側生成） | 日本語フォント（IPAex 等、OSS）を同梱し、オフラインで生成 |
| テスト | Vitest（単体・API統合）、Playwright（E2E） | 計算・採番・状態遷移は shared/server の単体テストで網羅 |
| 実行環境 | Docker Compose（`restart: unless-stopped`）、Node 24 LTS | DB はホストの `./data` にマウント（バックアップしやすくするため） |
| HTTPS | Caddy（リバースプロキシ）＋ mkcert のローカルCA | iPad Safari の Wake Lock・音声等の制約対策。CA証明書の iPad 配布手順を手順書化 |

**フェーズ1で確定したバージョン・実装上の決定**
- Node 24 / TypeScript 7 / React 19 / React Router 8 / Vite 8 / Fastify 5 / Socket.IO 4 / Drizzle 0.45 / Zod 4 / Vitest 5
- better-sqlite3 は **v12 系**に固定する。v13 は Windows + Node 24 向けのビルド済みバイナリが無く、開発機でネイティブビルドが必要になるため
- PIN・パスワードのハッシュは `@node-rs/argon2`（ビルド済みバイナリで導入できる）
- 管理画面は端末ペアリング不要とし、管理者ログイン（従業員コード + パスワード）で保護する。ペアリング対象はレジ・キッチン・カスタマー・ピックアップの4役割
- 端末トークンは `localStorage`（再起動後も維持）、ログインセッションは `sessionStorage` に保存し、それぞれ `X-Device-Token` / `X-Staff-Session` ヘッダーで送る。サーバーは SHA-256 ハッシュだけを保存する
- 従業員セッションは発行した端末でしか使えない。端末を無効化すると、その端末のセッション失効と即時切断を行う
- ペアリングとログインは失敗回数で一時的に拒否する（総当たり対策）
- 初回起動時、従業員が0人なら環境変数 `INITIAL_ADMIN_CODE` / `INITIAL_ADMIN_PASSWORD` で管理者を作成する

**PostgreSQL 移行への備え**：DBアクセスはリポジトリ層に閉じ込め、採番などの排他処理は「トランザクション内で行ロック相当を取る」インターフェースとして抽象化する（SQLite は `BEGIN IMMEDIATE`、PostgreSQL では `SELECT ... FOR UPDATE` に差し替え）。

金額はすべて整数（円）。販売・返金系は物理削除しない（論理的な取消・マイナス取引で表現）。

## 4. API・リアルタイムイベント設計（概要）

### REST（`/api`）
- 端末: `POST /devices/pair`（ペアリングコード→端末トークン）、`GET /devices/me`
- 認証: `POST /auth/login`（従業員コード+PIN）、`POST /auth/admin-login`、`POST /auth/manager-approve`（責任者PIN確認）
- レジ: `POST /register-sessions/open|close`、`GET /catalog`（商品・オプション・割引の一括取得）
- 会計: `POST /transactions`（**冪等キー必須**。注文・販売データ・採番を1トランザクションで確定）、`POST /transactions/quote`（サーバー側での金額試算）
- 注文: `GET /orders/active`、`POST /orders/:id/stations/:station/complete|undo`、`POST /orders/:id/call|recall|uncall|handover|undo-handover`
- 返金・変更: `GET /transactions/search`、`POST /transactions/:id/refund`、`POST /transactions/:id/exchange`
- 印刷: `GET /transactions/:id/receipt(.pdf)`、`POST /transactions/:id/reprint`
- 管理: 各マスタの CRUD、CSV入出力、`GET /reports/*`、`GET /audit-logs`

### Socket.IO
- 接続時に端末トークンで認証し、役割・ステーション別のルームに参加。
- サーバー→端末: `order.created` `order.updated` `order.stationUpdated` `order.called` `order.recalled` `order.removed` `catalog.updated` `settings.updated`
- すべてのイベントに `seq`（単調増加番号）を付与。端末は **接続・再接続のたびに `GET /orders/active` などで全状態を取り直し**、その後のイベントのみ適用する（要件4.2）。
- 状態変更はすべて REST 経由で行い、WS は通知専用にする（検証・権限・ログを一本化するため）。

### 状態遷移（サーバーで検証）
| 操作 | 遷移 |
| --- | --- |
| 呼び出し | accepted → calling |
| 呼び出し取消（undo） | calling → accepted |
| 受け渡し | accepted / calling → completed |
| 受け渡し取消（undo） | completed → calling（受け渡しから5分以内〔設定可〕かつ同じ番号が未使用の場合のみ） |
| 取消 | accepted / calling → cancelled |
| 受け渡し後の全額返金 | 状態は completed のまま。返金取引のみ記録 |

### 日次処理
- 管理画面の**閉店操作**で営業日を終了する（全レジ閉設済みであることを確認）。閉店時に DB バックアップ、自動採番のリセット（100へ）を行う。
- 閉店操作を忘れた場合は、営業日切替時刻に同じ処理を自動実行する。

### フェーズ3で確定した実装（上の案からの変更点を含む）
- **実際の API**（フェーズ1〜3）
  - レジ: `GET /api/register/registers`（レジ選択。ログイン前に端末認証だけで取れる）、`POST /api/register/sessions`（開設）、`GET /api/register/sessions/:id`（集計）、`POST /api/register/sessions/:id/close`（閉設）
  - 会計: `POST /api/transactions`。`POST /transactions/quote` は作らず、レジは共有パッケージの `priceOrder` で表示を計算し、確定時に `expectedTotal`（表示していた合計）を送る。サーバーの再計算と違えば 409 で確定しない
  - 注文: `GET /api/orders/board`（未完了＋直近12時間の受け渡し済み・取消を最大30件）、`POST /api/orders/:id/stations/:all|food|drink/complete|reopen`（キッチン端末のみ）、`POST /api/orders/:id/call|recall|uncall|handover|undo-handover`（ピックアップ端末のみ）
- **通知**: 注文は `order.updated`（`{ order, change }`）の1種類にまとめた。`change` は created / station_completed / station_reopened / called / recalled / uncalled / handed_over / handover_undone（フェーズ5で modified / cancelled を追加）。端末は `version` が手元より古い通知を捨てる
- **レジの流れ**: 要件3.1どおり、起動時にレジ番号を選んでからログインする。同じ端末で開設中のレジがあれば自動で再開する。店内／持ち帰りは会計ごとに必ず選ばせ、既定値を置かない（税率を取り違えないため）
- **採番**: 自動採番は前回の次の番号から、未完了の注文で使用中の番号を飛ばして採る。全番号が使用中なら 409。番号札は範囲内かつ未使用のみ受け付ける。レシート番号は `YYYYMMDD-レジ番号-4桁連番`
- **キッチン**: カードは1回のタップで完了（確認ダイアログなし）。誤操作は「直近に完了」から戻す。注文の状態（受付済み/呼び出し中）とステーションの完了は別に持つ
- **営業日**: 会計・開設のたびに、切替時刻で決まる営業日の行が無ければ作る。閉店操作（フェーズ6/7）を実装するまでは営業日が閉じられることはない

### フェーズ4で確定した実装（印刷基盤）
- **レイアウトの一元化**: `ReceiptDocument`（取引から作る）→ `buildReceiptLayout()` で行（text / pair / rule / space、文字サイズ normal / large / xlarge）に並べ、画面プレビュー・PDF・等幅テキストが同じ行を描く。将来の ESC/POS ドライバーも、この行を倍角コマンドに変換して使う
- **ドライバー**: `PrinterDriver { print(job), openDrawer() }`。当面は `DummyPrinterDriver`（受け付けてログに残すだけ）。レジごとのプリンター割り当ては `registers.printer_id` で、`PrinterRegistry` が選ぶ
- **PDF**: pdfkit（MIT）でサーバー側生成。80mm 幅・高さは内容に合わせる。フォントは Noto Sans JP（OFL、`@expo-google-fonts/noto-sans-jp` の TTF）を同梱し、使った文字だけ埋め込む（1枚 25KB 前後）
- **API**: `GET /api/transactions/:id/receipt`（行と等幅テキスト）、`GET /api/transactions/:id/receipt.pdf?reprint=0|1`、`POST /api/transactions/:id/reprint`（【再発行】と明記・操作ログ）。レジのログインか管理者ログインで使える
- **適格簡易請求書**: 登録番号・取引年月日・明細（軽減税率の対象に「※」と注記）・税率ごとの対象額（税込）・税率ごとの消費税額を必ず載せる。明細・金額は会計時の記録、店舗情報は出力時点の設定を使う
- **会計確定時**: 現金ならドロアを開く指示、続けてレシートの印刷指示をドライバーへ送る。応答は待たず、失敗してもログに出すだけ（会計は確定済み）

### フェーズ5で確定した実装（返金・変更）
- **記録の形**: 返金・商品変更は、元の販売に紐付く新しい取引（`kind = refund / exchange`）。返品した明細はマイナスの金額で元の明細を指し、追加した明細は正の金額で同じ取引に入る。差額（追加 − 返品）が取引の合計。元の販売データは一切変更しない
- **計上先**: 返金した日の営業日と、返金したレジの開設中セッション。現金返金はそのレジの理論在高を減らす（確認事項 Q13）
- **一部返金の金額**: 明細の支払額（割引の按分後）を数量で累積按分する。k 個目までの返金額 = floor(支払額 × k / 数量)、最後の1個で端数を吸収する。税率ごとの税額も累積で計算し、全額返金では元の税額をそのまま戻す
- **商品変更**: 追加する商品は会計と同じ検証（販売中・売切・必須オプション）を通し、元の会計の店内/持ち帰りで価格と税率を決める（割引は付けない）。差額は元の支払方法で精算する（確認事項 Q6）。追加した商品も後から返金できる
- **承認**: 責任者・管理者の従業員コード + PIN を確定のたびに入力し、理由とともに取引と操作ログに記録する
- **注文への反映**: 受け渡し前なら即座に反映（全額返金 → 取消、それ以外 → 「変更あり」と数量の変更、追加したステーションは未完了に戻す）。受け渡し済みは状態を変えない（確認事項 Q5）
- **API**: `GET /api/transactions`（検索）、`GET /api/transactions/:id/detail`、`POST /api/transactions/:id/refund-quote`、`POST /api/transactions/:id/refund`（冪等キー・`expectedDifference` 必須）
- **返金レシート**: 【返金】/【商品変更】、元のレシート番号、返品の明細（支払額をマイナス）、ご返金額と返金方法を載せる

### フェーズ6で確定した実装（売上・精算）
- **集計の定義**: 金額は割引後の税込。返金・変更は行った営業日・レジ・時刻に計上。純売上 = 総売上 + 返金・変更。客数 = 販売件数 − 全額返金された販売の件数（確認事項 Q10 の「会計件数」を基本に、全額返金で取り消された会計は除く）。客単価 = 純売上 ÷ 客数（切り捨て）。割引額 = 販売の割引 − 返金で戻した割引。商品別の数量は返品分を差し引く
- **期間**: 単日（営業日）が基本で、終了日を入れると期間（今日・昨日・直近7日・今月のボタンあり）
- **レジ点検・精算**: 開設中のレジは点検（現時点の理論在高）、閉設済みは精算結果（実査・過不足）。PayPay 売上は PayPay 側との照合用に出す
- **CSV**: summary / products / categories / hourly / payments / dining / taxes / discounts / registers / refunds / transactions（取引明細）/ settlements。BOM 付き UTF-8、全行の先頭に店舗コード・開始日・終了日（要件4.1）
- **操作ログ**: 分類（返金・変更／割引／価格変更／マスタ・設定／レジ開設・閉設／端末・ログイン／レシート）で絞り込み、50件ずつ新しい順。変更前後の内容を表示
- **API**: `GET /api/admin/reports/sales`、`GET /api/admin/reports/settlements`、`GET /api/admin/reports/:kind.csv`、`GET /api/admin/audit-logs`（すべて管理者ログイン必須）
- **画面**: 管理画面の最初のページを「売上」にした。指標はタイル、時間帯別は1系列の棒グラフ（DADS ブルー600、ツールチップ、表に切替可）

### フェーズ7で確定した実装（運用）
- **閉店操作**（確認事項 Q9）: 管理画面から。開設中のレジがあれば拒否。閉じた営業日には会計・開設できない（誤操作は「営業を再開」で戻す）。閉店時にバックアップ
- **自動閉店**: サーバーが1分ごとに、切替時刻を過ぎても開いたままの営業日を閉じ、バックアップを取る（閉設していないレジはログに警告を出し、開設のまま残す）
- **採番のリセット**: 自動採番は営業日ごとのカウンタを使うので、営業日が変われば開始番号から振り直される。閉店時に別のリセット処理は行わない
- **バックアップ**: better-sqlite3 のオンラインバックアップ（WAL で書き込み中でも一貫）。`backups/pos-<店舗コード>-<営業日>-<日時>.sqlite`、`BACKUP_KEEP` 世代（既定 30）。閉店時・自動閉店時・手動。別媒体への持ち出しは cron の rsync を手順書で案内
- **復元**: `scripts/restore.sh`。アプリのイメージ内で整合性チェック → アプリ停止 → 今の DB を退避 → 入れ替え → 起動・ヘルスチェック
- **自動起動**: `restart: unless-stopped` と `systemctl enable docker`。コンテナのログは 10MB × 5 世代
- **管理者パスワードの復旧**: `ADMIN_PASSWORD_RESET=1` と `INITIAL_ADMIN_*` を設定して起動
- **キオスク**: Chrome の自動再生を許可して起動すれば、カスタマーモニターとキッチンはタップなしで音が鳴る（許可しない場合は起動時に1回タップ）
- **手順書**: `docs/setup-guide.md`（Ubuntu の準備から構築・端末設定・毎日の運用・バックアップと復元・更新と移設・困ったとき・構築後のチェックリスト）

## 5. 計算ルール（案・テストで固定する）

1. 明細金額 = (単価 + オプション加算額合計) × 数量
2. 明細割引: 金額はそのまま、率は明細金額×率を**切り捨て**
3. 会計割引: 金額はそのまま、率は（明細割引後の合計）×率を**切り捨て**
   - 割引は明細・会計とも**複数適用可**。適用した順に計算し、率割引は「それまでの割引を引いた後の金額」に掛ける。明細・会計とも金額が0円未満にならないよう、超過分は割引額を減らして0円で止める
4. 会計割引の按分: 税率グループごとの金額比で按分し各々切り捨て、**残り端数は金額の大きい税率グループへ寄せる**（同額なら10%側）。一部返金用に明細単位にも同じ方式で按分して保存
5. 税額: 税率ごとの税込合計から `合計 × 税率 / (100 + 税率)` を1回だけ端数処理（既定: 切り捨て、設定で四捨五入/切り上げ）
6. 税率決定: 軽減対象 × 店内 = 10%、軽減対象 × 持ち帰り = 8%、対象外 = 常に10%

| 9 | 営業日の終了 | **閉店操作を設ける**。忘れた場合は切替時刻に自動実行 |
| 10 | 客数 | **会計件数**（人数入力なし） |
| 11 | 割引の重ね掛け | **明細・会計とも複数可**（0円未満にならない範囲で） |
| 12 | 端末とレジ番号 | **起動時に選択**。同じレジ番号を2台で同時に開設できない |
| 13 | 現金返金の出所 | **返金を行ったレジ**の理論在高を減らす |
| 14 | HTTPS | **mkcert のローカルCAを各端末にインストール**する運用。手順書化する |

**セット商品のステーション判定**：注文がステーションの明細を持つかは「商品のステーション」と「選択されたオプションのステーション」の両方で判定する。どちらにも該当がないステーションは最初から完了扱い。
